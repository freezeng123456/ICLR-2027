## 线 2：PFN 先验掰动

### 1. 背景是什么，基线是什么，做的是什么问题

**背景。** PFN（Prior-data Fitted Network，先验数据拟合网络）是这样一类模型：先在**合成
任务**上大规模预训练，用的时候不训练，把带标签的样本当上下文塞进去，一次前向就出预测。
表格数据上的 TabPFN、TabICL 都是这一类，2026 年它们已经在 TabArena、TALENT 这些基准上
超过了调过参的 CatBoost / XGBoost。

它的定义性特征是：**PFN 的预测在数学上等价于"在它预训练时那个先验下做贝叶斯后验推断"。**
先验是什么，由合成数据的生成器决定，训练完就固定了。

**问题。** 既然先验是固定的，那当真实任务不在这个先验的支撑内（先验错配）时会怎样？
答案是它会**系统性地答错，而且错得有方向**——它给出的是"在它自己先验下的正确答案"，
不是真实机制下的正确答案。

于是问题变成：**能不能不重新训练，只靠往上下文里塞人为构造的样本（anchor），
把这个先验"掰"到别处去？** 如果能，那 in-context 样本就不只是"证据"，
还是一个**作用在先验上的算子**——这是对 PFN 上下文学习的一个重新理解。

**这里有个必须挡住的替代解释。** 加了样本之后预测变了，最平凡的解释是"多了几个近邻，
局部信息变多了"。要排除它，做法是**把 anchor 全部放在离查询点极远的位置**——远到在真实
长度尺度下函数相关性实际为零，任何基于近邻检索的方法都会把它们当无关样本丢弃。
如果预测仍然改变，起作用的就只能是先验被掰动这条路径。

**基线。** 分两条线（完整盘点见 [08-PFN基线盘点.md](08-PFN基线盘点.md)）：

*自训小 GP PFN*（有解析解，能逐点核对答案）——四个解析参照：
- **P 下的混合后验**：按边际似然对长度尺度网格加权，这是"PFN 应该给出的答案"
- 用真实长度尺度算的后验：数据生成机制的 oracle
- 固定 ℓ=1.0 的后验：排除"它只是用了一个固定设定"
- 全预测 0：平凡基线

*真实表格 PFN（TabICLv2）*——以"不加 anchor"为基准，加两个对照：
- **随机标签 anchor**：同位置同行数但标签纯随机，扣掉"多了一批远处行"本身的副作用
- **额外真实数据**：同样行数的目标任务真实样本，作为增益的上界

统计一律同种子配对，报 t 值。

### 2. 目前想用什么方法，希望优化的指标是什么

**方法。** 构造远置 anchor，其标签由**与目标任务完全无关**的另一条规则生成——因此不含
任何关于答案的信息，唯一携带的是"这个任务是什么结构"。两组 anchor 的行数、特征分布、
位置全部相同，只有生成标签的那个结构维度不同，所以归一化、上下文长度这些副作用被完全
抵消。

试过两个"结构维度"（也就是想掰动的那个先验隐变量）：

| 轴 | 做法 | 结果 |
|---|---|---|
| **平滑度**（硬阈值规则型 vs 处处可导的平滑型） | 结构匹配 anchor vs 结构不匹配 anchor | **失败**。结构匹配的 anchor 并不优于随机标签 anchor，结构信息没传进去 |
| **噪声水平**（anchor 标签的翻转率 η） | η 从 0 扫到 0.5，做剂量反应 | **成立**。置信度随 η 单调下降，说明模型从上下文推断出一个全局噪声水平，并用到了与该 anchor 无关的目标任务上 |

中间还做了一个诊断实验（`exp_locality.py`）来区分"轴选错了"和"远处的行压根没被读"——
把**确实含目标任务信息**的 anchor 放在不同距离上，看增益如何随距离衰减。

**指标。** 按实验分：

- GP 线：对各解析参照的 **RMSE**；掰动部分用 Δ_PFN 对 Δ_解析后验的**相关系数与斜率**
  （斜率 1.0 = 完全跟随理论），以及先验隐含长度尺度的前后变化
- 表格线早期：**准确率**
- 表格线噪声轴：准确率 + **平均置信度**（对先验移动灵敏得多，准确率太迟钝）
- 最新一步（`exp_noise_steer.py`）：**log loss 为主**（严格适当评分规则，同时反映准确与
  校准），辅以 **ECE**（纯校准）和准确率（纯决策）

**最新一步在赌什么。** 既然 anchor 噪声能把置信度拉低，那它就应该是**可控的杠杆**：
目标任务本身噪声大、模型过度自信时，用高噪声 anchor 压下来；任务干净时用低噪声 anchor
保持锐利。判据是**是否出现交叉**——最优 anchor 噪声是否随目标任务真实噪声上升而上升。
出现交叉才说明这是个工具，否则只是个单向副作用。

**这一步最大的风险**（见 [08](08-PFN基线盘点.md) 第一条）：审稿人会立刻问
"我直接做温度缩放不行吗"。那是一行代码的单参数方法。**目前没有跑这个对照**，
而它决定了这个结果算不算数。

## 顺带：为什么你的推送一直失败

`Failed connect to github.com:443; Connection timed out`，说明分支根本没推上去，
原因是**超算登录节点到 github.com:443 的出网不通**（API 走 curl 能通，git 的 443 通道
超时）。三次重试全部失败，`PUSH_FAIL_SIGMA`。

这不是脚本的问题——前两次确实是引号转义炸了，但第三次脚本已经跑通到 `PUSHING_SIGMA`，
死在网络上。要绕开的话：走已经能通的 HTTPS API 路径（`git bundle` + Release/artifact
上传），或者用 SSH 端口 443（`ssh.github.com:443`）试试，或者在有外网的机器上中转。
