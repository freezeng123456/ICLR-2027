# 只有 2 张 H20：选题重排与执行方案

这份文档在 [02-选题建议.md](02-选题建议.md) 的基础上，把算力约束加进来重新排序。
结论是**排序变了**，而且有一个原本排第一的候选要往后放。

## 一、这台机器到底是什么

单卡 H20（NVIDIA 官方规格）：

| 指标 | H20 | H100 SXM | H20 / H100 |
|---|---:|---:|---:|
| 显存 | 96 GB HBM3 | 80 GB HBM3 | **1.20×** |
| 显存带宽 | **4.0 TB/s** | 3.35 TB/s | **1.19×** |
| BF16/FP16 稠密算力 | **148 TFLOPS** | ~989 TFLOPS | **0.15×** |
| FP8 / INT8 | 296 TFLOPS | ~1,979 TFLOPS | 0.15× |
| TF32 / FP32 | 74 / 44 TFLOPS | — | — |
| NVLink | 900 GB/s | 900 GB/s | 1.0× |
| TDP | 350–400 W | 700 W | 0.5× |

两张合起来：**192 GB 显存、8 TB/s 聚合带宽、296 TFLOPS BF16**。

**这张卡的定义性特征是算术强度失衡。** 把峰值算力除以带宽，得到"每读一字节需要配多少次
浮点运算才能喂饱计算单元"：

- H20：148e12 ÷ 4.0e12 = **37 FLOP/byte**
- H100：989e12 ÷ 3.35e12 = **295 FLOP/byte**

差了 8 倍。意思是：**H20 的内存系统比 H100 还强，计算单元只有 H100 的 1/6.7。**
凡是卡在搬数据上的活儿，H20 干得比 H100 还好；凡是卡在算数上的活儿，H20 慢六七倍。

### 一个不太符合直觉、但直接决定排期的推论

网上到处都说"H20 是推理神卡"。这个说法**只在低并发、看延迟的场景下成立**，而研究实验
恰恰是相反的场景——离线批量推理，只看吞吐。做一下解码阶段的 roofline：

对一个 8B 的 BF16 模型（权重 16 GB），batch 为 B 时的单步解码：

- 读权重的时间 = 16 GB ÷ 4.0 TB/s = **4.0 ms**（与 B 无关）
- 算数的时间 = 2 × 8e9 × B ÷ (148 TFLOPS × 40% MFU) ≈ **0.27 × B ms**

两者在 **B ≈ 15** 时相等。也就是说，**batch 超过 15 之后 H20 的解码就变成算力瓶颈了**，
吞吐封顶在约 3,700 tok/s（单卡）。同样的计算在 H100 上，crossover 落在 B ≈ 118，
封顶约 24,700 tok/s。

所以做批量实验时，**H20 相对 H100 的劣势就是那个 6.7 倍，一分都不会少**。带宽优势只在
小 batch 时兑现，而你不会用小 batch 跑实验。

规划用的量级（BF16、大 batch、**两卡合计**）。"理论封顶"由
[`analysis/hardware_budget.py`](../analysis/hardware_budget.py) 算出，"规划用"是打了
六七折的保守值：

| 模型规模 | 权重 | 理论封顶 | 规划用 | 说明 |
|---|---:|---:|---:|---|
| 7–8B | 16 GB | 7,400 tok/s | **~5,000** | 单卡放得下，两卡跑两份副本比 TP=2 更划算 |
| 14B | 28 GB | 4,200 tok/s | ~2,800 | |
| 32B | 64 GB | 1,850 tok/s | ~1,200 | TP=2 |
| 70B | 140 GB | 850 tok/s | ~550 | TP=2，192 GB 里只剩 52 GB 给 KV，batch 上不去 |

注意最后一行：70B 在 2 张 H20 上**装得下但跑不动**——不是显存问题，是算力问题。
它只适合用来做少量关键对照，不能当主力模型。

> 这些都是 roofline 推的上限，实测通常只有理论值的 30–60%。**第一周就自己测一遍**，
> 别拿它们做承诺。方法：用你的实际推理栈跑 `vllm bench throughput`，固定输入/输出长度、
> 扫 batch、记录饱和吞吐，然后把实测的 MFU 传回脚本重算：
>
> ```bash
> python3 analysis/hardware_budget.py --params 8 --mfu 0.25
> ```

## 二、擅长和不擅长什么

**擅长**（H20 在这些事上不比 H100 差，甚至更好）：

- **把一个大开源模型完整放在本地当研究对象。** 192 GB 能装下 70B 的 BF16，或 140B 级的
  FP8。你能拿到 logits、隐状态、精确的采样种子、确定的引擎版本——这些 API 模型给不了。
  这是这台机器最被低估的能力。
- **KV cache 常驻的长上下文解码。** 显存大、带宽高，长序列的解码阶段是它的主场。
- **高并发、彼此独立的短任务。** 几万个互不依赖的推理任务可以铺满 batch。
- **命中 prefix cache 的 agent 循环**（下面会展开，这是最重要的一条）。

**不擅长**：

- **任何像样的训练。** 296 TFLOPS 合计，连 7B 的全参微调都很慢，RL post-training 更是
  在算力瓶颈上硬顶。
- **长上下文的 prefill。** prefill 是纯算力活儿，而且注意力部分是 O(n²)。8B 模型上
  一次 8k prefill 约 2.8 秒、32k 约 18 秒、**128k 约 3.1 分钟**（同样条件下 H100 分别是
  0.4 秒、2.7 秒、28 秒）。128k 时注意力项占了总算力的 81%，是它在爆炸。这条直接砍掉了
  一整类实验设计。
- **扩散语言模型。** dLLM 每个去噪步都要对整个序列做一次完整前向，比自回归解码贵一到
  两个数量级，而且是纯算力型开销。这是 H20 最差的工况。
- **需要大量训练 run 的消融。** 只有两张卡，跑不了并行 sweep。
- **任何分布式/并行相关的研究。** TP 最多到 2，没有多机，模型必须塞进 192 GB。

## 三、算力预算的实际数字

从今天（08-03）到正文截止（09-25）是 **53 天**。

| 项 | 数值 |
|---|---:|
| 理论上限 | 53 天 × 24 h × 2 卡 = **2,544 GPU·h** |
| 扣掉最后 12 天写作、画图、内部评审 | −576 |
| 扣掉第 1 周环境搭建与试点 | −336 |
| 扣掉调试、跑挂、发现 bug 后重跑（按 35% 计） | −571 |
| **能真正产出论文里那些数字的** | **约 1,060 GPU·h ≈ 530 小时墙钟** |

530 小时墙钟大约是 22 天不间断运行。按上表 8B 的规划值 5,000 tok/s 算，这个预算大概是
**96 亿输出 token**；换成 32B 就只剩约 23 亿，70B 只剩约 10 亿。

同一个脚本可以直接算这张表，改截止日或开销比例即可：

```bash
python3 analysis/hardware_budget.py --params 8 --deadline 2026-09-25 --overhead 0.58
```

**这个预算的含义**：一个 8B 规模的纯推理研究绰绰有余；32B 要精打细算；70B 只能用来做
少量的关键对照，不能当主力。**任何需要训练的方案都要先把训练那部分单独立项算清楚。**

## 四、重排后的选题优先级

原来的排序只考虑了拥挤度。把算力加进来之后：

| 候选 | 拥挤度 | 算力匹配度 | 综合 | 变化 |
|---|---|---|---|---|
| **A2-b** agent benchmark 运行间方差 | 低 | **极佳**——纯推理、短上下文、天然可批量、必须本地 GPU | **第一** | ↑ 升到唯一首选 |
| **A5** 撤销已失效的用户偏好 | 中 | **好**——多轮但每轮短，成本主要在设计不在算力 | 第二 | ↑ 从第四升上来 |
| **A1-a** memory vs 等预算长上下文 | 低 | **中**——长上下文 prefill 是 H20 死穴，必须限定预算上限 | 第三 | ↓ 从并列第一降下来 |
| **A2-c** 污染对排名的扰动 | 低 | 好——纯推理 | 第四 | — |
| **B1** 给经验现象一个理论解释 | 低 | **不受影响**——几乎不吃算力 | 机会成本最低 | ↑ 相对变得更值 |
| **A2-a** LLM-as-judge 统计效力 | 中 | 好 | 备选 | — |
| **A4** diffusion LM | 中 | **差**——每步全序列前向，纯算力型 | 放弃 | ↓↓ 硬件否决 |
| **A1-b** RLVR verifier | 高 | **差**——要跑 RL | 放弃 | — |
| **A1-c** test-time scaling 转负 | 高 | 中 | 放弃 | — |
| **A3** KV 压缩 / 低比特量化 | 很高 | **反向禁忌**（见下） | 放弃 | — |

### 为什么 A3 从"红海"变成"硬件禁忌"

除了拥挤，现在多了一条独立的否决理由：**在 H20 上测出来的效率结论不能外推。**
H20 的算术强度是 37 FLOP/byte，H100 是 295——差 8 倍。一个 KV 压缩方法在 H20 上省下的
是访存，而 H20 的访存本来就不紧张、算力才紧张；同样的方法搬到 H100 上，瓶颈完全在另一边。
你测出的加速比在别的卡上大概率复现不了，而审稿人一定会问这个问题。

（顺带一提，"效率方法的排序在不同机器平衡点上不可迁移"本身是个好选题，但它需要至少
三种算术强度差异明显的卡才能立论，两张同型号 H20 做不了。）

### 为什么 A4（diffusion LM）被硬件否决

masked dLLM 生成长度 L 的序列需要 T 个去噪步，每步都是对**整个序列**做一次完整前向。
即使每步定 8 个 token（T = L/8），总算力也是自回归带 KV cache 解码的约 L/8 倍——L=512
时是 64 倍。而且这些是大矩阵乘，纯算力型，正好压在 H20 最弱的地方。叠加 H20 相对 H100
的 6.7 倍劣势，同样的实验你要花别人几十倍的时间。

这个方向的选题价值没有变（小池子、高接收率、刚拿了 ICML Outstanding），**但它需要
算力型的卡**。如果后面能借到 H100/A100 再说。

## 五、第一选择：A2-b，而且硬件把它从"能做"变成了"只有你能做"

原本 A2-b 的问题是"agent benchmark 跑 10 次方差有多大"。有了本地 GPU，可以把它做成一个
更完整、也更难被抢的东西：**把 agent 评测的方差拆成三个来源，分别定量。**

1. **采样随机性**——temperature、top-p 带来的。
2. **环境随机性**——网页变化、工具超时、沙箱状态。
3. **推理引擎的非确定性**——即使 temperature=0、种子固定，**改变 batch 大小或张量并行度
   就会改变输出**。原因是浮点加法不满足结合律，而 reduction kernel 的切分方式随 batch
   形状变化。

第三条是关键：**它必须在本地 GPU 上研究，用 API 根本做不了**，因为你控制不了对方的
batch 调度。2 张 H20 在这里不是限制，是准入条件。

**查重结果**：非确定性的*机制*已经有人做了——《Beyond Reproducibility: Token
Probabilities Expose Large Language Model Nondeterminism》（[2601.06118](https://arxiv.org/abs/2601.06118)）、
《Introducing Background Temperature to Characterise Hidden Randomness in LLMs》
（[2604.22411](https://arxiv.org/abs/2604.22411)）、
《Deterministic Inference across Tensor Parallel Sizes》（[2511.17826](https://arxiv.org/abs/2511.17826)）；
judge 侧的可复现性也有《Necessary but Not Sufficient: Temperature Control and
Reproducibility in LLM-as-Judge Safety...》（[2606.26185](https://arxiv.org/abs/2606.26185)）。
最接近框架层面的是《CAFE: A Compound-AI Factorial Evaluation Framework》
（[2607.10380](https://arxiv.org/abs/2607.10380)）。

**所以论文的贡献不能是"非确定性存在"**——那已经不新了。还开着的是**回溯审计**：
建立噪声带之后，回头去量化**已发表的 agent 改进里有多少落在噪声带内**。这才是有冲击力
的那一半，而且和 A2-a 的建议是同一个模式。措辞上用聚合统计（"在我们抽样的 N 篇论文中，
x% 的主要结论在 95% 置信水平下不显著"），不要点名。

**为什么这个组合适合 H20**：agent 任务彼此独立，可以同时铺几百个 episode 把 batch 填满；
单个任务上下文通常在 8k–32k，避开了长 prefill；重复运行 10 次这件事本身就是"同一批 prompt
反复跑"，prefix cache 命中率极高。

## 六、A1-a 的重新 scoping

A1-a（memory 系统 vs 等预算长上下文）的科学价值没变，但**必须把长上下文那一臂的预算上限
从 128k 砍到 32k**。原因就是前面那个数字：8B 模型上一次 128k prefill 要约 3 分钟，
而这个实验需要成千上万次。

粗算一下：假设 4 个 memory 系统 × 3 个 benchmark × 5 个预算档 × 100 episode × 3 seed
= 18,000 个 episode。如果长上下文档位设在 128k，光 prefill 就是 18,000 × 3 min ÷ 2 卡
≈ **450 小时墙钟**——把整个预算吃光，还没算生成部分。设在 32k 则是约 50 小时，可行。

**怎么把这个限制变成论文的优点**：本来就是"等 token 预算下的对照"，那把预算轴限定在
1k–32k 反而更贴近真实部署（绝大多数 agent 系统的实际上下文预算就在这个区间）。再补一个
128k 的小规模抽查（比如 200 个 episode）说明趋势外推成立即可。**在论文里明写清楚预算
上限和理由**，比让审稿人自己发现要好。

## 七、工程决策清单

这几条在 H20 上是数量级差别，不是调优细节。

- [ ] **用 vLLM 或 SGLang，绝对不要用 HF `transformers` 的 `generate` 跑实验。**
      吞吐差一个数量级，直接决定实验做不做得完。
- [ ] **打开 automatic prefix caching。** agent 循环每一轮都把不断变长的历史重新送进去，
      不开缓存要重复 prefill 整个前缀。一个 20 轮、上下文涨到 30k 的 episode，
      开缓存约 30k token 的 prefill，不开约 300k——**10 倍差距，而且卡在 H20 最弱的
      prefill 上**。
- [ ] **8B 级模型跑两份独立副本，不要 TP=2。** 单卡放得下时，TP 只会引入通信开销并
      降低总吞吐；两份副本是线性加速。TP=2 留给 32B 以上。
- [ ] **主实验用 BF16，不要用 FP8 省时间。** FP8 确实能把峰值算力翻倍（148→296 TFLOPS），
      但它引入一个数值精度的混淆变量。如果你的论文主张恰恰是"某个效应很微妙"，
      审稿人会问是不是量化造成的。FP8 只用于扩展性抽查，且要在论文里单独说明。
- [ ] **固定并记录整个软件栈的版本**：推理引擎版本、CUDA、kernel 后端、batch 调度参数、
      张量并行度。做非确定性研究时这些就是实验变量；做别的研究时它们是必须报告的
      可复现性信息。
- [ ] **上下文长度是预算的二次项。** 任何实验设计先算一遍 prefill 总量，再决定长度上限。
- [ ] **能借到算力型的卡就借。** 一次 128k 的抽查、或者一个小 RL 试点，租几十个
      H100 小时就够，能显著降低风险。不要为了纯净性放弃这条。

## 九、如果只能记住三句话

1. **H20 的劣势是算力，不是显存。** 凡是"多跑几遍推理"的实验，这台机器够用；凡是
   "训练"或"超长 prefill"的实验，直接换题，不要试图硬扛。
2. **选 A2-b。** 它是唯一一个硬件从限制变成准入条件的选题——研究推理引擎的非确定性
   必须有本地 GPU，而它的实验形态（大量独立短任务、高 prefix cache 命中率）正好是
   H20 的主场。贡献点要放在**回溯审计**上，不是"非确定性存在"。
3. **第一周先测吞吐，再定实验规模。** 本文所有算力数字都是 roofline 推出来的，误差
   可能有两倍。用实测值重算一遍第三节的预算表，再决定模型规模和实验矩阵。
